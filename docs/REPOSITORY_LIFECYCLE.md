# Repository lifecycle

This document defines the repository-level lifecycle that surrounds product code: research, validation-authority qualification, release preparation, immutable release, external laboratory qualification, and evidence retention.

## Research lifecycle

Research branches are temporary execution surfaces, not durable evidence stores. Durable lineage lives in `.github/research/evidence-index.json`.

Allowed lifecycle states are `ACTIVE`, `ACCEPTED`, `REJECTED`, `SUPERSEDED`, `ABANDONED`, and `UNCLASSIFIED`. Only terminal records with an exact branch-head SHA and sealed evidence may be marked `gc_eligible`. Automatic GC additionally requires `auto_gc=true`, a live branch SHA that still matches the registry, and no open pull request.

`Research Branch GC` is fail-closed. A protected-main merge may automatically remove only exact registry entries marked `auto_gc`; any SHA drift or open PR blocks the apply transaction before deletion. Manual apply requires the explicit confirmation string `DELETE_GC_ELIGIBLE_REFS`.

## Validation-authority qualification

One-way holdout qualification uses `Validation Authority Qualification`. The caller provides an exact 40-hex candidate SHA and acknowledges `ONE_WAY_HOLDOUT`. The workflow freezes a fingerprint over the canonical evaluator, exact correlation backend, hosted-AEC policy, and dataset lock before calling the reusable Hosted Real AEC workflow against that exact SHA.

An acoustic holdout failure rejects the candidate. Threshold, search, or metric tuning from holdout feedback is forbidden. Compiler/import/infrastructure wiring failures may be corrected without changing the frozen acoustic candidate semantics.

Normal pull-request, main-push, and scheduled Hosted Real AEC validation remain unchanged.

## Release preparation

`scripts/prepare_release.py` is the canonical release-metadata helper. It updates only the CMake project version and prepends a new CHANGELOG section; `--base-ref` verifies that historical CHANGELOG content below the new release heading is byte-for-byte unchanged.

Release-bearing authority remains governed by `scripts/ci_impact.py`. A CMake change that modifies only the project VERSION token is classified as `VERSION_ONLY` for PR matrix selection, while main pushes still force the complete verification graph.

## Immutable release evidence

Future releases include a machine-readable release evidence manifest generated by `scripts/release_manifest.py`. It binds the exact source commit/tree, merged PR lineage, main Verify run, validation-authority hashes, packaged asset digests, and the initial external-lab availability state.

The manifest does not weaken release authority. A new version is released only after a successful main-push Verify, through the existing exact-SHA Release workflow and immutable tag/release governance.

The v2.3.6 release predates the integrated manifest asset; its evidence is backfilled without mutating the immutable release in `docs/releases/v2.3.6-evidence.json`.

## External laboratory status

Software release status and external laboratory qualification are separate state domains. Post-release HIL and Extended Real workflows remain fail-visible; disabled infrastructure must not report a fake PASS.

The normalized lab states are `PASS`, `FAIL`, `BLOCKED_RUNNER`, `BLOCKED_CONFIG`, `PENDING`, and `UNKNOWN`. `Post Release Qualification Summary` emits a JSON artifact and Actions summary that preserve this distinction.

## Evidence retention versus branch retention

Deleting a terminal research branch does not delete its commit objects immediately and does not remove referenced Actions artifacts, pull-request discussions, release assets, immutable tags, or registry lineage. Branch names are therefore not used as the long-term evidence authority.
